# Правила роботи ШІ з проєктом

Перевірено за кодом: 2026-09-10. Точка входу: [README](README.md).

## Перед змінами

1. Прочитай `docs/README.md`, `docs/DECISIONS.md` і відповідний тематичний документ.
2. Перевір `git status --short` та наявні інструкції репозиторію. Збережи незакомічені зміни користувача.
3. Знайди повний шлях сценарію: маршрут → middleware/Gate → controller/request → use case/model → відповідь → React-сторінка.
4. Звір припущення з кодом. У проєкті співіснують старі й нові підходи; не використовуй типовий шаблон Laravel замість дослідження реалізації.
5. Переглянь `KNOWN_ISSUES.md`: незавершений сценарій не слід вважати готовою залежністю.

## Орієнтири реалізації

- Eloquent-моделі розташовані в `app/Entity`, не в типовій директорії `app/Models`.
- У старших модулях бізнес-операції організовано через `app/UseCases`; у курсах значна частина логіки знаходиться в моделях і контролерах. Підтримуй локальний стиль, якщо задача не передбачає рефакторинг.
- Зміни статусів оголошень, банерів, користувачів і звернень проводь через наявні доменні методи, враховуючи їхні перевірки та побічні ефекти.
- Авторизацію перевіряй на сервері. Прихована кнопка React та оголошений, але невикликаний Gate не захищають операцію.
- Для вкладених ресурсів перевіряй належність дочірнього запису батьківському.
- Змінюй контракт Inertia props разом з його споживачем. Імена сторінок мають відповідати `resources/js/Pages` з урахуванням регістру.
- У курсах зберігай поля `_uk` і `_en`, порядок `position`, ознаки публікації та зв'язки.
- Структуру БД змінюй новими міграціями; враховуй старі таблиці з префіксами `advert_` і `ticket_`.
- Для черг, пошуку та файлів перевіряй побічні ефекти окремо від запису в БД.
- Не змінюй `vendor`, `node_modules`, кеші та згенеровані assets як джерело реалізації. Не оновлюй обидва JS lock-файли без потреби; CI використовує npm.
- Не копіюй секрети з `.env`, логів або платіжного коду в документацію. Для опису конфігурації використовуй назви змінних та `.env.example`.
