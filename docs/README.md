# Документація системи

Актуальність аналізу: 2026-09-10. Джерело — код поточного робочого дерева. Це жива документація для власника проєкту та ШІ, який його змінює.

## З чого почати

1. Прочитати [правила роботи ШІ](AI_GUIDE.md).
2. Переглянути [архітектуру](ARCHITECTURE.md) та потрібний розділ [доменів і даних](DOMAIN_MODEL.md).
3. Для змін HTTP/UI читати [маршрути та frontend](HTTP_AND_FRONTEND.md).
4. Перед запуском — [розробка й перевірки](DEVELOPMENT.md).
5. Перед реалізацією перевірити [відомі обмеження](KNOWN_ISSUES.md) та [рішення власника](DECISIONS.md).

## Як підтримувати документацію

- Опис реалізованої поведінки зберігати в тематичних файлах. Плани та побажання позначати явно й записувати в `DECISIONS.md`.
- При зміні коду оновлювати відповідну документацію в тому самому наборі змін.
- Зберігати посилання на файли-джерела; не дублювати повний код, схему БД або весь список маршрутів.
- Для нового висновку зазначати дату, джерело та спосіб перевірки: аналіз коду, тест або ручна перевірка.
- Після виправлення проблеми змінювати її статус у `KNOWN_ISSUES.md` і додавати доказ перевірки.
- Зберігати уточнення власника; не перегенеровувати файли зі стиранням ручних доповнень.

Код показує поточну реалізацію, рішення власника — потрібну поведінку. Якщо вони відрізняються, це розбіжність, яку потрібно зафіксувати, а не мовчки усунути в документації.

## Межі аналізу

Проаналізовано залежності, bootstrap, маршрути, ключові моделі, контролери, сервіси, UI, міграції, тести та Docker/CI. Це не повний аудит безпеки. PHP у локальному shell відсутній; backend, міграції, зовнішні сервіси та браузерні сценарії не запускалися. Наявність коду не означає підтвердженої працездатності.
